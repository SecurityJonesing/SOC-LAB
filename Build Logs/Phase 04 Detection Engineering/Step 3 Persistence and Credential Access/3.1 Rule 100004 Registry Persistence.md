## 3.1 Rule 100004 Registry Persistence

**Phase:** 4, Detection Engineering
**Goal:** Write a custom Wazuh rule detecting registry Run and RunOnce key persistence (T1547.001), building on the pattern established with `100002` and `100003`.
**Rollback:** Snapshot `pre-atomic-persistence-20260811` (Win11-LTSC-Victim), no manager side snapshot taken, config only change, `local_rules.xml` copies retained throughout.
**Transcript:** session spanning 2026-08-13 evening into 2026-08-14.

### What happened
Staged Atomic Red Team test T1547.001-1 (Reg Key Run), writes `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run\Atomic Red Team` via `reg.exe`, with a clean single command cleanup. Ran it, confirmed the registry value landed (`Get-ItemProperty`), then confirmed Sysmon captured it as Event ID 13 with `RuleName: T1060,RunKey`, SwiftOnSecurity's own config already tags this pattern. Confirmed Wazuh's built in rule `92302` (level 6, generic registry entry modified using reg.exe) already catches this, but non specifically, the actual gap being filled.

Found the stale local file problem before writing anything new. `~/local_rules.xml` on `wazuh-host` still had the broken, pre fix version of `100002` and `100003` (old `data.win.*` namespace, bare `decoded_as`), never updated after the live container copy was fixed directly in the prior session. Deleted the stale local file and re pulled the real, current, working version straight from the container before touching anything, avoiding a rule regression.

Designed rule `100004`, writing the actual XML: `<if_group>sysmon_event_13</if_group>`, `<field name="win.eventdata.targetObject" type="pcre2">(?i)CURRENTVERSION\\\\(RUN|RUNONCE)\\\\</field>`, level 14, MITRE T1547.001. Field path (`win.eventdata.targetObject`) and the four backslash escaping convention were both confirmed directly against Wazuh's own built in rule `92300` (same file, `0860-sysmon_id_13.xml`) rather than assumed, `92300`'s working regex uses the identical `\\\\` pattern for a single literal backslash, confirming PCRE2's own doubling plus this ruleset's XML level doubling stack to four.

Deployed via `docker exec -u wazuh ... sh -c 'cat > ...' < ~/local_rules.xml` (avoiding `docker cp`'s known ownership reassignment bug from the prior session), verified ownership stayed `wazuh:wazuh`, validated with `wazuh-analysisd -t` (exit code 0), restarted only the manager container.

Rule did not fire. Re ran the atomic test, searched `rule.id:"100004"` in Discover, no results, while `rule.id:"92302"` on the same fresh event did return a hit. Confirmed via direct `archives.json` grep that `100004` had never matched a single event since going live, despite passing syntax validation. Field value (`targetObject`) confirmed correct via the raw archive JSON. Attempted `wazuh-logtest` for a definitive rule trace, but it stalled at Phase 2 (decoding) for every test event, confirmed as a `wazuh-logtest` specific artifact rather than evidence about `100004` itself.

Root cause, found via live event capture (`tail -f archives.json` while re running the atomic test): Wazuh's rule engine evaluates root level rules in ruleset file load order and stops at the first matching root rule for a given event, it does not continue testing other independent root level rule groups afterward. Built in rule `92300` (root level, `<if_group>sysmon_event_13</if_group>`, broad pattern covering essentially any `...CurrentVersion\Run...` write) loads before `local_rules.xml` and claims the event first, since its pattern is broad enough to match the atomic test. `100004`, also root level via `<if_group>`, never got evaluated, confirmed by `archives.json` showing only one `rule` object per event line (`92302`), never two.

Fix: changed `100004`'s dispatch from `<if_group>sysmon_event_13</if_group>` to `<if_sid>92300</if_sid>`, chaining as a child of the built in rule that already claims these events, the same pattern `92301`, `92302`, and `92303` themselves use, rather than competing as an independent root level rule. Re validated, restarted, re tested: `100004` fired correctly, confirmed in `archives.json` (`"id":"100004"`, level 14, correct description and MITRE tag) and independently confirmed live in the Wazuh dashboard on a fresh atomic test run.

### Outcome
- Rule `100004` is live, verified, and correctly detecting T1547.001 Run and RunOnce key persistence, chained under `<if_sid>92300</if_sid>`, firing alongside built in rule `92302` as a sibling child of the same matched parent.
- Local `local_rules.xml` on `wazuh-host` is now confirmed in sync with the container's live copy.
- This is a genuinely reusable structural lesson for every future custom rule that chains via `<if_group>` rather than `<if_sid>`: any root level group gated rule can be silently short circuited by an earlier loading built in rule with a broader pattern on the same event. `100002` and `100003` were not immune to this, they simply had not hit it yet at this point.

### Lessons
1. Wazuh's rule engine stops at the first matching root level rule per event, it does not evaluate all independent root rule groups against the same event. A custom root level `<if_group>` rule can be silently starved by an earlier loading, broader built in rule that claims the event first. Invisible from XML syntax validation alone.
2. Chaining via `<if_sid>` onto a specific already matched rule guarantees independent, sibling evaluation, the same mechanism `92301` through `92303` use as children of `92300`.
3. `wazuh-logtest` fed raw JSON directly uses the generic `json` decoder, not the production decoder, this can prevent event dispatch from ever reaching decoder specific rule groups. Verify against real, live captured production events before concluding a rule is broken.
4. Local working copies of rules files can silently drift from the deployed, fixed version inside the container if a prior session's fix was applied directly via `docker exec` or `docker cp` without also updating the local file.
5. When confirming an escaping or field path convention, check it against a real, currently working built in rule in the same rules file rather than deriving it from first principles.
