## 3.2 Rule 100005 LSASS Silent Process Exit

**Phase:** 4, Detection Engineering
**Goal:** Write a custom Wazuh rule detecting T1003.001 credential dumping, building on the pattern established with `100002`, `100003`, and `100004`.
**Rollback:** Snapshot `pre-atomic-credaccess-20260817` (Win11-LTSC-Victim), taken before any T1003 activity.
**Transcript:** session spanning evening of 2026-08-17.

### What happened

**Sub technique selection.** Chose T1003.001 (LSASS Memory) over T1003.002 (SAM), .003 (NTDS, no domain controller yet), and .006 (DCSync, planned for a later phase), LSASS is the most common real world credential dumping technique, works standalone without a domain, and lines up with the new telemetry (Sysmon Event ID 10, ProcessAccess) flagged at session start.

**First attempt, T1003.001-2 (comsvcs.dll MiniDump) blocked twice, at two different layers.** AMSI blocked the script outright (`ScriptContainedMaliciousContent`) until a Defender exclusion was added for `C:\AtomicRedTeam`. After that, the test failed differently, `Access is denied` starting the process. Root caused via direct registry check: `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\RunAsPPL = 2`, LSASS is running as a UEFI locked Protected Process Light, a real Windows 11 hardening feature blocking non protected processes from opening handles to LSASS at all. Confirmed via Sysmon: zero Event ID 10 entries exist anywhere in the log for this attempt, PPL blocks the access before Sysmon's kernel callback ever sees it. This is a legitimate defensive finding, not a lab misconfiguration.

**Pivoted to T1003.001-14 (Silent Process Exit via nanodump)**, a technique that abuses WerFault.exe (which runs with its own elevated access) to dump LSASS on process exit, rather than the attacker's own process opening a handle directly. This test requires the third party `nanodump.x64.exe` binary, which the atomic test's own prereq step downloads from GitHub.

**Staging friction, several rounds:**
1. RANGE30 has no internet by design, the download had to happen on the management PC and be staged onto the victim VM via ISO, same pattern as prior sessions.
2. Bitdefender on the management PC blocked the download and, separately, blocked the file mid copy into the ISO staging folder, required two rounds of exclusion (first a narrow file level exclusion, which did not fully take due to the elevation gotcha already documented; then a broader folder level exclusion with Bitdefender confirmed running as Administrator).
3. First ISO build silently produced a corrupted filesystem, 45KB output (smaller than the 108KB source binary), and mounting it showed `EXTERNALPAYLOADS` as unreadable and corrupted. Root cause: Bitdefender likely touched the file mid `oscdimg` write, before the folder level exclusion was confirmed in force. Cleaned up and rebuilt from scratch under the confirmed exclusion, second build succeeded (153,600 bytes, contents verified readable via mount before uploading).
4. Uploaded to Proxmox `local` storage, attached to VM 101, copied `nanodump.x64.exe` into `C:\AtomicRedTeam\ExternalPayloads\` on the victim, confirmed via `-CheckPrereqs`.

**Ran the test, Defender blocked it again, via a different mechanism than PPL.** Exit code 0, but nanodump self reported "WerFault did not create the dump." Checked `Get-MpThreatDetection` and the real time Defender Operational event log directly, which showed the actual cause: two named cloud and behavioral signatures, `Behavior:Win32/LsassDump.G` and `Behavior:Win32/LsassDump.H`, fired on the exact IFEO registry writes the technique makes, not a folder path scan, so the existing exclusion did not help.

**This turned out to be the actual detection opportunity, not just a blocker.** The named signatures fired on:
- `HKLM\...\Image File Execution Options\lsass.exe\GlobalFlag` (DWORD `0x00000200`, `FLG_MONITOR_SILENT_PROCESS_EXIT`)
- `HKLM\...\SilentProcessExit\lsass.exe\...` (DumpType, LocalDumpFolder)

Checked Sysmon directly for the underlying registry events, confirmed Event ID 12 (DeleteKey) and Event ID 13 (SetValue) both captured, tagged `RuleName: T1183,IFEO` by SwiftOnSecurity's config, with the real `GlobalFlag = 0x00000200` value visible in the raw event. This is a legitimate, narrow, high fidelity artifact, almost nothing legitimate sets this specific value on `lsass.exe`'s IFEO key.

**Clock skew discovered and fixed, mid session, as a real environment correctness issue.** While checking whether the archive pipeline had actually captured the test events, found the manager's archive file had not been updated in 20 plus minutes despite ongoing agent activity, turned out the victim VM's clock was running roughly 2 hours ahead of real time, from two independent causes: timezone set to Pacific instead of Central, and even after fixing the timezone, the underlying system clock itself was still off by a separate roughly 2 hour drift. Fixed both, `Set-TimeZone -Id "Central Standard Time"`, then `Set-Date` to match the management PC's real time. Verified via `(Get-Date).ToUniversalTime()` matching `wazuh-host`'s own `date -u` output afterward.

**Designed and deployed rule `100005`**, writing the actual XML: chained via `<if_sid>61615</if_sid>` (Event 13's real dispatch rule, confirmed live via `grep` against `0595-win-sysmon_rules.xml`, no built in rule already covers IFEO and lsass), single field condition on `win.eventdata.targetObject` matching `Image File Execution Options\\lsass\.exe\\GlobalFlag` (case insensitive, correct four backslash doubling convention), level 14, dual MITRE tags T1003.001 (credential access objective) and T1546.012 (the actual IFEO injection mechanism).

**Verification took several wrong turns before landing on the right method.** `wazuh-logtest` fed raw JSON via stdin matched only the generic syslog catch all, confirmed this is the same `json` versus `windows_eventchannel` decoder mismatch already documented for `100004`'s troubleshooting. Realized the actual blocker: the archived test event being checked (01:52:54 UTC) predated the manager's restart and rule load time (02:10:42 UTC), a pure sequencing issue, not a rule problem. Ran one more fresh atomic test after the rule was confirmed loaded, then checked `archives.json` directly, rule `100005` fired correctly, confirmed via the real alert JSON: `"id":"100005"`, level 14, both MITRE tags present, correct auto derived tactics and techniques, `firedtimes: 1`, timestamped 02:32:31 UTC, well after the rule went live.

**Claude Code SSH incident.** When delegated the diagnostic pass, Claude Code could not resolve the host alias `wazuh-host` and, rather than stopping to ask, looped through eighteen different guessed usernames against the live host before finally stopping to ask for the correct one. The correct username was already documented in `PROJECT-INSTRUCTIONS.md`'s Claude Code allow rule the whole time. No lockout or security impact, but a new standing rule was added to `PROJECT-INSTRUCTIONS.md` prohibiting username and credential guessing loops going forward.

### Outcome
- Rule `100005` is live, verified, and correctly detecting T1003.001/T1546.012 (Silent Process Exit LSASS credential dumping), chained under `<if_sid>61615</if_sid>`, confirmed firing end to end against real atomic test traffic via direct `archives.json` inspection.
- Three custom detections spanning three tactics at this point: `100002` and `100003` (Execution, T1059.001), `100004` (Persistence, T1547.001), `100005` (Credential Access, T1003.001/T1546.012).
- Two real defensive layers documented as legitimate findings, not obstacles: LSASS PPL (UEFI locked) blocking direct memory access outright, and Defender's named behavioral signatures catching the Silent Process Exit technique via its registry footprint even when the direct access path is already closed.
- Win11-LTSC-Victim's clock is now correctly set (Central timezone, drift corrected).
- New standing rule added to `PROJECT-INSTRUCTIONS.md`: Claude Code must never guess at credentials or usernames against any host, stop and report back on the first failure with the documented credential instead.

### Lessons
1. LSASS PPL (`RunAsPPL=2`, UEFI locked) blocks direct handle credential dumping techniques before Sysmon's ProcessAccess callback even fires, zero Event ID 10 telemetry is itself the signal that PPL intervened.
2. A technique blocked by AV or EDR is not a dead end for detection engineering, the artifact left behind by the blocked attempt can be the detection itself.
3. Clock skew can masquerade as a broken detection pipeline. Two independent causes existed simultaneously, fixing one did not fix the other, both needed checking.
4. `wazuh-logtest` fed raw JSON via stdin does not reliably reproduce the real Sysmon rule matching path in this Wazuh version. Direct `archives.json` inspection against a real, freshly generated, correctly timed test event remains the more reliable verification method.
5. When delegating diagnostic work to an automation tool, always confirm it has the correct connection details before it starts, an unresolvable host alias or missing credential should trigger one clarifying question, not a guessing loop.
6. A test event's timestamp must be checked against the rule load timestamp before concluding a rule is not firing.
