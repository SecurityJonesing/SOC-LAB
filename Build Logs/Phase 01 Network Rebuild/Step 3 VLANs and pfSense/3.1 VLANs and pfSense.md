# Step 3: VLANs and pfSense

## 2026-07-21, NIC troubleshooting and vmbr3 creation

**Phase:** 1
**Goal:** Identify NIC3 physically, create a trunk capable bridge for pfSense LAN.
**Rollback:** None needed, no destructive changes, only bridge creation (additive) and interface up/down toggles.
**Transcript:** console and SSH, this date.

### What happened

Chassis port labels were confirmed NOT self-evident from `ip link show` alone, had to physically trace cables to labels. Confirmed the management NIC both by physical inspection and behaviorally (unplugging it dropped the SSH/management session).

The other three NICs all showed `state DOWN` / `Link detected: no` across multiple cables, multiple switch ports, and even a direct PC-to-server connection, appeared to rule out cabling entirely. Extensive troubleshooting followed: `lspci`/`dmesg` (all 4 NICs detected cleanly by the kernel, no driver errors), BIOS Integrated Devices check (all 4 ports Enabled), iDRAC Lifecycle Log/SEL review (no explicit NIC fault logged).

Root cause, finally found: the other three NICs were simply never administratively brought up (`ip link show` showed no `UP` flag). Physical hardware was never at fault. Fix: `ip link set <iface> up` on each, all three immediately showed `LOWER_UP` and clean `1000Mb/s Full duplex` link once brought up.

Created vmbr3 via the Proxmox GUI: bridge port on NIC3, no IP, VLAN aware enabled (`bridge-vids 2-4094`). Applied via GUI, took effect live, no reboot needed. Confirmed written to `/etc/network/interfaces` (persistent). Naming chose `vmbr3` (matching NIC3) instead of the "next sequential" `vmbr2`, a deliberate one off exception to keep NIC to bridge naming legible.

### Outcome

All 4 physical NICs confirmed healthy. vmbr3 created, VLAN aware, ready for pfSense's LAN interface in the next step.

### Lessons

1. Check administrative interface state (`ip link set <iface> up`) BEFORE any hardware level troubleshooting. A DOWN interface with no UP flag looks identical to a real hardware fault. This is now the FIRST thing to check on any "port shows no link" problem.
2. Chassis port labels are not reliable without physical confirmation.
3. Bridge names don't have to match NIC numbers, but once one convention exists, decide deliberately.

## 2026-07-21, vmbr0 to vmbr2 swap, missing gateway fix, package upgrade and reboot

**Phase:** 1
**Goal:** Rename NIC2's bridge to match the NIC-number convention, discovered and fixed a missing default gateway in the process, upgraded and rebooted pve01.
**Rollback:** None needed, vmbr0 had no IP/no VMs attached (safe to delete), gateway addition tested live before persisting, package upgrade left prior kernels installed and selectable in GRUB as fallback.
**Transcript:** console and SSH, this date.

### What happened

Deleted vmbr0 via the Proxmox GUI. Confirmed removed both live and in `/etc/network/interfaces`. Created vmbr2 on NIC2: no IP, VLAN aware left unchecked (this is pfSense's planned WAN side, not a VLAN trunk).

While troubleshooting `apt update` failures (all repos "Network is unreachable"), `ip route show` had no default route, only the local subnet route via vmbr1. `/etc/network/interfaces` confirmed no gateway line existed anywhere despite an earlier log entry stating one was added. Root cause of the discrepancy not determined.

Fix: added `gateway 192.168.0.1` under vmbr1's `iface` stanza, `ifreload -a`. Verified live: `ip route show` showed the new default route, `ping 192.168.0.1` and `ping 8.8.8.8` both succeeded, SSH session stayed connected throughout.

Ran `apt update`, succeeded once the gateway was fixed. Reviewed `apt list --upgradable` before proceeding: two kernel packages, pve-manager, qemu-server, pve-firewall, pve-container, ZFS packages, standard Debian libs, no unexpected removals. Confirmed both existing VMs were stopped before reboot. Rebooted. Confirmed post reboot: new kernel active, vmbr1/192.168.0.201 up, default route persisted, ping to 8.8.8.8 succeeded.

### Outcome

- NIC2/vmbr2 = no IP, no VMs, ready for pfSense WAN.
- NIC1/vmbr1 = management, 192.168.0.201/24, now with a working default gateway, confirmed persistent across reboot.
- pve01 fully patched.
- Current bridge state: vmbr1 (NIC1, management), vmbr2 (NIC2, pfSense WAN, unconfigured), vmbr3 (NIC3, pfSense LAN trunk, VLAN aware, unconfigured), NIC4 unbridged.

### Lessons

1. A "no default gateway" symptom can look identical to a DNS or firewall problem, check `ip route show` early when package manager connectivity fails entirely.
2. A prior log entry stating a change was made is not the same as confirming it's still true. Verify current state against the live system before trusting a past log entry.
3. `qm snapshot` only covers VMs, not the bare metal host, the actual fallback for a host level package upgrade is confirming prior kernels remain selectable in GRUB.
4. Before any host level `apt upgrade` involving a kernel, confirm all VMs' running state first.

## 2026-07-23, VLAN creation, trunk to pfSense, management access port

**Phase:** 1
**Goal:** Create the three VLANs, configure the trunk port to pfSense (NIC3/Gi1/0/3), put the management PC's port into the Management VLAN.
**Rollback:** None needed for VLAN creation (additive). Config saved to NVRAM only after each step's output was confirmed correct.
**Transcript:** PuTTY (switch, COM14), this date.

### What happened

Pre-check, `show run` reviewed before touching anything, confirmed the switch still matched the clean factory reset baseline.

Step 4, created VLANs 10 (MGMT), 20 (INFRA), 30 (RANGE):

```
enable
configure terminal
vlan 10
 name MGMT
vlan 20
 name INFRA
vlan 30
 name RANGE
end
show vlan brief
```

`show vlan brief` confirmed all three as `active`, no ports assigned yet. Clean on the first attempt.

Step 5, trunk port to pfSense (Gi1/0/3). Identified which physical port NIC3 was actually cabled into via `show interfaces status`, Gi1/0/3 was the only port showing `connected`, matching NIC3.

```
enable
configure terminal
interface GigabitEthernet1/0/3
 switchport trunk encapsulation dot1q
 switchport mode trunk
 switchport trunk allowed vlan 10,20,30
end
show interfaces trunk
```

`switchport trunk encapsulation dot1q` was rejected (`% Invalid input detected`), expected, this 2960X only supports 802.1Q natively. First pass missed the `switchport trunk allowed vlan 10,20,30` line, appears to have been dropped from a paste, `show interfaces trunk` still showed trunking/802.1q correctly even with it missing, but "Vlans allowed on trunk" read `1-4094`, not `10,20,30`, caught on closer inspection. Re-ran the missing line, confirmed correct afterward.

Step 6, management PC's access port. Original plan was `Gi1/0/48` directly, but the PC's cable was actually running through the home dumb switch as a shared uplink, not a dedicated line. Fix: used a USB-to-Ethernet adapter to run a dedicated point-to-point link directly into `Gi1/0/48`, bypassing the dumb switch. Configured `Gi1/0/48` as access mode, VLAN 10. `show vlan brief` confirmed it listed under VLAN 10.

`Gi1/0/49`/`Gi1/0/50` still showed `err-disabled` even after the full factory reset, pointing to a hardware level fault rather than leftover config.

Saved config: `copy running-config startup-config`, confirmed written to NVRAM.

### Outcome

- VLANs 10/20/30 created and active.
- Gi1/0/3 trunking correctly scoped to 10,20,30 only.
- Gi1/0/48 in VLAN 10 access mode, a dedicated point-to-point link from the PC (via USB-Ethernet adapter).
- Switch config saved to NVRAM.
- Gi1/0/49/Gi1/0/50 flagged as likely hardware faulty.
- The pfSense VM itself still not built, bridges exist, but no VM attached to them.

### Lessons

1. A missing line in a multi-line paste can silently succeed, always compare every relevant field, not just whether the command was accepted.
2. `end` typed at the top level EXEC prompt (not inside a config sub-mode) is not a no-op, IOS tries to resolve it as a hostname/telnet target instead.
3. A "management port" assumption should be physically verified, not taken on faith.
4. Ports staying `err-disabled` after a full factory erase is a hardware fault signal, not a config leftover.

## 2026-07-24, pfSense VM built and installed

**Phase:** 1
**Goal:** Build the pfSense VM on pve01, attach it to the two existing bridges, get pfSense CE actually installed and booted.
**Rollback:** None needed, new VM, no prior state.
**Transcript:** console/web UI + PuTTY (switch, for pre-checks), this date.

### What happened

Pre-checks: confirmed the Netgate Installer ISO was present. Re-verified the WAN/LAN-trunk bridges live rather than trusting the prior log entry, both initially showed `NO-CARRIER`/`DOWN`, traced to the Cisco switch simply being powered off since last session. Powered the switch back on, both bridges came up correctly.

VM creation (VM 102, named `pfsense`): OS "Other" guest type, ISO = Netgate installer bootstrap image, disk 32GB VirtIO SCSI, CPU/RAM started 2 cores/2GB, bumped to 3 cores/4GB mid-install because first boot resource usage pegged out. Network: `net0` to WAN bridge, `net1` to LAN-trunk bridge, no VLAN tag at this layer.

Installer walkthrough: WAN interface confirmed via MAC match, DHCP client. LAN interface confirmed via MAC match and by the switch showing Gi1/0/3 connected. Internet connectivity check failed first (WAN had no physical cable yet), fixed by plugging NIC2's physical port into the dumb switch. Subscription validation: no Plus subscription, selected Install CE. Software version 2.8.1. Filesystem ZFS, Stripe, GPT. Installation completed cleanly. Halted (not rebooted) before removing installer media.

First real boot succeeded: pfSense 2.8.1-RELEASE amd64, "Bootup complete." Console menu confirmed both interfaces live: WAN via DHCP from the dumb switch, LAN at the factory default static address.

### Outcome

pfSense CE 2.8.1 installed and running, attached to both bridges correctly. Web GUI not yet reachable from the management PC, LAN currently only knows the factory default subnet, not the real VLAN subnets.

### Lessons

1. The Netgate Installer needs internet access on WAN to complete installation.
2. A build log entry is a snapshot, not a guarantee, re-verify live state.
3. VM resource allocation may need temporary headroom for first boot/install.
4. MAC address cross-checking between Proxmox's Hardware tab and the guest OS's interface-selection screen is reliable.

## 2026-07-25, pfSense VLAN interfaces, setup wizard, first snapshot, acceptance check passed

**Phase:** 1
**Goal:** Create the three VLAN sub-interfaces inside pfSense, assign real subnets, confirm the web GUI is reachable from the Management VLAN, take a clean rollback snapshot.
**Rollback:** Snapshot `pfsense-clean-install` taken at the end of this session.
**Transcript:** Proxmox VM console (pfSense) + browser (pfSense GUI), this date.

### What happened

VLAN sub-interfaces created via the console menu: tag 10 (Management), tag 20 (Infra), tag 30 (Range).

IP assignment via the console menu, static, no upstream gateway on any of the three, DHCP server enabled:
- LAN (Management): 10.10.10.1/24, DHCP range 10.10.10.100 to 10.10.10.199
- OPT1 (Infra): 10.10.20.1/24, DHCP range 10.10.20.100 to 10.10.20.199
- OPT2 (Range): 10.10.30.1/24, DHCP range 10.10.30.100 to 10.10.30.199

Client-side confirmation: the management PC's USB-Ethernet adapter picked up a DHCP lease, 10.10.10.100/24, gateway 10.10.10.1. Browsed to `https://10.10.10.1/` and reached pfSense's login page. This is Phase 1's acceptance check, passed.

Logged in, forced password change immediately. Ran the pfSense setup wizard: "Block RFC1918 Private Networks" was checked by default on WAN, unchecked it since this build's WAN faces the home network, itself an RFC1918 range. Left "Block bogon networks" checked. Reloaded configuration, wizard completed cleanly.

Snapshot taken: `pfsense-clean-install`, VM running, RAM not included.

### Outcome

Phase 1 is now fully complete. All steps done: VLANs created, trunk configured and scoped correctly, management PC's access isolated via a dedicated USB-adapter link, pfSense VM built and installed, VLAN interfaces created and IP addressed, GUI reachability confirmed from the Management VLAN. pfSense reachable at `https://10.10.10.1/` from any device on the Management VLAN. First rollback point for the pfSense VM exists (`pfsense-clean-install`).

### Lessons

1. "Block RFC1918 Private Networks" on WAN is the wrong default for a home lab topology where WAN's upstream is itself a private network.
2. The pfSense setup wizard re-displaying already-configured values rather than blank defaults confirms it reads and preserves existing config.
3. A live VM snapshot (no RAM) is sufficient for a configuration checkpoint.
