# Step 2: Switch Identification and Reset

## 2026-07-17, Identifying the Cisco switch

**Phase:** 1
**Goal:** Identify the Cisco switch before writing any command for it, model, IOS version, real interface names.
**Rollback:** None needed, show commands are read only.
**Transcript:** PuTTY logging, set before connecting.

### What happened

Connected via PuTTY, COM14, 9600/8/1/None/None. Ran:

```
enable
show version
show interfaces status
```

Full `show version` output confirmed:

```
Cisco IOS Software, C2960X Software (C2960X-UNIVERSALK9-M), Version 15.2(7)E9, RELEASE SOFTWARE (fc1)
...
cisco WS-C2960X-48FPS-L (APM86XXX) processor (revision V0) with 524288K bytes of memory.

1 FastEthernet interface
52 Gigabit Ethernet interfaces

```

The switch was already enabled (prompt was `Lab-Switch>` moving to `Lab-Switch#` after a password that already worked), so no password recovery was actually needed on this pass.

### Outcome

Model: WS-C2960X-48FPS-L, IOS: 15.2(7)E9. Interface naming: `GigabitEthernet1/0/1` through `1/0/52` (shorthand `Gi1/0/1`), plus a separate `Fa0` management port.

Port summary (pre-config baseline, from `show interfaces status`):
- Gi1/0/1, Gi1/0/48-52: VLAN 1 (default)
- Gi1/0/2-47: VLAN 10 (leftover from a prior config, wiped in the factory reset below)
- Gi1/0/49-50: err-disabled (later confirmed hardware-faulty)
- Gi1/0/51-52: "Not Present" (unpopulated SFP/stacking ports)
- All ports notconnect, nothing cabled yet.

This also confirmed the switch already carried a prior configuration (hostname `Lab-Switch`, most ports in VLAN 10, ports 49/50 err-disabled), consistent with the blueprint's note that it arrived untrusted and needed a full wipe.

### Lessons

None, this is a read only identification step. See the factory reset entry below for the actual configuration change.

## 2026-07-17, Cisco switch factory reset

**Phase:** 1
**Goal:** Wipe the switch to factory defaults, confirm clean console access, before any VLAN or trunk config.
**Rollback:** None needed, intentional planned reset.
**Transcript:** PuTTY, COM14.

### What happened

```
enable
write erase
```

Output: `Erasing the nvram filesystem will remove all configuration files! Continue? [confirm]` then `Erase of nvram: complete`.

```
reload
```

First `reload` attempt: answered the `[confirm]` prompt with "n" instead of Enter, which cancelled the reload, NVRAM was erased but the switch kept running the old configuration in RAM. Caught this before assuming the reload had happened.

Re-ran `reload`, pressed Enter at `[confirm]` this time:

```
--- System Configuration Dialog ---
Would you like to enter the initial configuration dialog? [yes/no]: n
Switch>enable
Switch#
```

Session log had garbage lines from an accidental clipboard paste (right-click in PuTTY pastes clipboard directly, a chat response happened to be on the clipboard at the time), the switch correctly rejected all of it as invalid input, no actual config impact. Confirmed clean via a follow-up `show run`.

Verified clean state: `enable` required no password, `show run` showed hostname "Switch" (default), no VLAN assignments, no err-disabled state, all 52 Gi ports at default, no aaa or line passwords configured.

Ran `write memory`, confirmed saved config matched the verified clean running config exactly. Powered off the switch normally at an idle prompt.

### Outcome

Switch factory reset confirmed clean, saved to NVRAM, powered down safely. Console access confirmed working post reset. Old hostname (`Lab-Switch`), old VLAN 10 assignments, the err-disabled state on ports 49/50, and whatever password was set, all gone.

### Lessons

1. On Cisco, `[confirm]` prompts want Enter, any other keystroke (including "n") cancels the action rather than confirming "no." Different from a `[yes/no]` prompt, which takes a typed answer.
2. Right-click in PuTTY pastes the OS clipboard directly as keystrokes with no preview. Check clipboard contents before right-clicking, or use left-click-drag to select and copy just the intended text.
