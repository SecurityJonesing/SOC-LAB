### What happened

Step 2, host prep. Set `vm.max_map_count=262144` live, then persisted it to `/etc/sysctl.conf` via `echo "..." | sudo tee -a`, confirmed necessary because a plain `sudo echo ... >> file` would fail: the shell sets up `>>` redirection using the calling user's own permissions before sudo ever runs, so only `tee` (itself elevated by sudo) can actually write to a root-owned file this way.

Step 3, Docker + Compose, official apt method. Ran the defensive removal of six potentially-conflicting packages, all six came back "not installed," a clean baseline. Added Docker's GPG key and the official repo. Installed the Docker CE package set, clean install, `docker.service`/`docker.socket` both enabled via systemd. Verified via `systemctl status docker` and `docker run hello-world` (a real test of INFRA20's HTTPS rule against Docker Hub). Added the primary user to the docker group for non-root usage. Required a full SSH session restart (group membership is read at login, not live), confirmed via `groups` and a passwordless `docker run hello-world` retry.

Step 4, Git, identity, SSH, clone. Git was already present (2.43.0, stock on 24.04). Set the Git identity. Generated a fresh ED25519 keypair on wazuh-host itself, deliberately separate from pve01's existing key. Added the public key to GitHub as a repo-scoped Deploy Key (not an account-level key) with write access enabled.

`ssh -T git@github.com` hung on first attempt, diagnosed immediately as the same INFRA20 gap pattern from the DNS/ICMP issue during the OS install: port 22 (SSH) was never in the original four rules, so it fell to implicit deny with no response either way. Added a 5th Pass rule to INFRA20, TCP/22, description "allow INFRA20 -> SSH (22)".

Retried `ssh -T git@github.com`, connected, host key fingerprint manually verified against GitHub's officially published fingerprint before accepting. Cloned the repo via SSH, clean, no errors.

Docx workbook retirement (documentation cleanup, not lab infrastructure). Discovered the repo's working folder is actually the repo root itself, not a subfolder holding old transcripts as previously assumed, confirmed via `git remote -v`. Reviewed all five `.docx` files in the workbook folder, decided explicitly to delete all five and treat the four `.md` files as the sole source of truth going forward. Deleted the folder locally, used `git add -A` after confirming via `git status` that exactly the five expected files showed as deleted and nothing else. Committed and pushed.

`agent-registry.md` replaced with a real governance scaffold. `PROJECT-INSTRUCTIONS.md` rewritten in first person throughout, folding in facts that had drifted out of sync.

### Lessons

1. Any new port/protocol beyond the original four INFRA20 rules needs its own explicit Pass rule.
2. `sudo command >> file` silently fails on root-owned files even though the command itself is elevated. `echo "..." | sudo tee -a file` is the correct pattern.
3. A folder's name inside a git repo, including the folder holding `.git` itself, is not tracked by git and can be renamed freely with zero repo-side consequences.
4. Deploy keys, not account-level SSH keys, are the right scope for a single-repo, single-purpose credential.
5. Maintaining parallel documentation formats (markdown + docx) doubles the update burden for no real information gain.
