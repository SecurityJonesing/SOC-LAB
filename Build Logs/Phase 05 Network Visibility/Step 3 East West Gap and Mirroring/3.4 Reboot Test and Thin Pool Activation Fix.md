## Part 2, the SPAN session was never saved

Checking persistence before trusting it. My first try ran from `Switch>` user mode and failed with `% Invalid input detected`, because `show startup-config` needs privileged mode. After `enable`:
```
show startup-config | include monitor
```
No output. The SPAN session existed only in running-config. A switch reload would have brought `Gi1/0/4` back as a plain VLAN 1 port and silently cut the physical north-south feed to Suricata. The session surviving today only means the switch itself had not been power-cycled since the SPAN was configured.

Before saving, I checked what else was unsaved, so that `write memory` would not persist anything unintended:
```
show running-config | include monitor
show startup-config | include switchport mode trunk
show archive config differences nvram:startup-config system:running-config
```
The running config holds both `monitor session 1` lines. The `Gi1/0/3` trunk (`switchport mode trunk`) is already in startup-config. The diff syntax works on IOS 15.2(7)E9 without `archive` configured, and it showed only two differences: the two `+monitor session 1` lines, and a cosmetic difference in how the self-signed `TP-self-signed-1224086528` certificate is stored. No unintended changes were pending.

**Rollback path (stated before the change):** back up startup-config to flash first. If the save went wrong, `copy flash:startup-config-pre-span-20261031 startup-config` and a reload would restore it. `write memory` does not touch the live running config, so it could not affect the trunk or `Gi1/0/48` management access.

Backup:
```
copy startup-config flash:startup-config-pre-span-20261031
Destination filename [startup-config-pre-span-20261031]? Y
2930 bytes copied in 0.060 secs (48833 bytes/sec)
```
I typed `Y` at the destination filename prompt, which IOS took as the filename. `dir flash:` showed the backup saved as `Y`, 2930 bytes. I renamed it:
```
rename flash:Y flash:startup-config-pre-span-20261031
```
pressing Enter at the confirmation prompt. `dir flash:` then showed `startup-config-pre-span-20261031`, 2930 bytes, the same size as `config.text`, with 40,836,096 bytes free.

Save and verify:
```
write memory
Building configuration...
[OK]
show startup-config | include monitor
monitor session 1 source vlan 30
monitor session 1 destination interface Gi1/0/4
```
The SPAN session now survives a switch reload.

## Part 3, no VM would start: thin pool activation failure

`qm list` showed all four VMs stopped, and none of them have `onboot` set:
```
for v in 100 101 102 103; do echo "VM $v:"; qm config $v | grep -E "onboot|hookscript|startup"; done
```
VMs 100, 101, and 103 returned only `hookscript: local:snippets/suricata-mirror-hook.sh`. VM 102 returned nothing. Every start is manual, which fits the nightly shutdown habit.

Every `qm start` failed the same way:
```
activating LV 'pve/data' failed:   Activation of logical volume pve/data is prohibited while logical volume pve/data_tmeta is active.
```
`pvesm status` showed `local` active (32.40% used), but `local-lvm` (lvmthin) `inactive` with all zeros. `systemctl --failed` listed zero failed units. The `pvecm status` error (`corosync.conf does not exist`) is expected on a standalone node. The `/var/lock/qemu-server/` lock files were normal leftovers.

Read-only diagnosis:
```
lvs -a -o lv_name,lv_attr,lv_size,pool_lv,data_percent,metadata_percent pve
```
```
  data                                               twi---tz-- <10.77t
  [data_tdata]                                       Twi-a----- <10.77t
  [data_tmeta]                                       ewi-a----- <15.88g
  [lvol0_pmspare]                                    ewi------- <15.88g
  root                                               -wi-ao----  96.00g
```
plus every VM disk, saved state, and snapshot (`BeforeClaudeCode`, `pfsense-clean-install`, `Pre-Suricata`, the `pre-atomic-*` set, and the rest), all still listed. The thin pool `data` was inactive while its two hidden components, `data_tdata` and `data_tmeta`, were each active on their own outside the pool. LVM refuses to assemble a pool while its components are active separately.
```
dmsetup info -c
```
`pve-data_tdata` and `pve-data_tmeta` both mapped with an open count of `0`, and there was no `pve-data` pool device. Nothing was using the stray components.
```
journalctl -b --no-pager | grep -iE "thin_check|thin|lvm2|pve/data|pve-data" | head -40
```
`lvm2-monitor` started normally at 16:02:56–57. The first failure was `pvestatd` at 16:03:47, retrying every 10 seconds. There was no `thin_check` failure and no "Check of pool failed" line, so there was no evidence of metadata damage.

**Likely cause, not proven:** a boot-time activation timeout on a large pool (10.77 TiB data, about 16 GiB metadata) left the components active and the pool unassembled. The roughly one-minute `thin_check` seen in Part 4 is consistent with that.

I considered just rebooting, but captured the evidence first: a non-persistent journal would lose the only record of the cause, and a persistent cause would just repeat.

## Part 4, the fix

**Rollback path (stated before the change):** deactivating an unused component only removes a kernel mapping and writes nothing to disk. Pool activation runs `thin_check` first and refuses if the metadata is bad. `pve-root`, swap, and the VM configs were untouched. Fallback: a reboot returns to the same state, with iDRAC at `192.168.0.100` for a hang.

Syntax confirmed against the live version first (`lvm version`: `2.03.31(2) (2025-02-27)`).

Step 1:
```
lvchange -an pve/data_tmeta
lvs -a -o lv_name,lv_attr pve | grep -E "data |tdata|tmeta"
  data                                               twi---tz--
  [data_tdata]                                       Twi-a-----
  [data_tmeta]                                       ewi-------
```
Step 2:
```
lvchange -an pve/data_tdata
```
No output. The following `lvs` hung for about a minute. `pvestatd`'s 10-second retry had started activating the pool, so `lvs` was waiting on the VG lock while `thin_check` ran. I left it to finish rather than interrupt it, since interrupting `thin_check` is the one move here that could make things worse. When it returned:
```
  data                                               twi-aotz--
  [data_tdata]                                       Twi-ao----
  [data_tmeta]                                       ewi-ao----
```
The pool is active and open, with both components in use by it. A separate pool activation step was not needed.

Confirmation:
```
pvesm status; lvs -o lv_name,data_percent,metadata_percent pve/data
local-lvm     lvmthin     active     11559493632       324821771     11234671860    2.81%
  data 2.81   1.13
```
The journal timeline proves the sequence: `pvestatd` was blocked by `data_tmeta` until 17:06:52, by `data_tdata` from 17:07:01 to 17:07:51 (after Step 1), and then:
```
Oct 31 17:08:52 Pve01 kernel: device-mapper: thin: Data device (dm-3) discard unsupported: Disabling discard passdown.
Oct 31 17:08:53 Pve01 dmeventd[12355]: Monitoring thin pool pve-data-tpool.
```
The discard line is informational: the disks behind the R710's RAID controller do not support discard. `dmeventd` monitoring the pool is the healthy end state.

## Lessons

1. Running-config is not saved config. A SPAN session can work for months and still vanish on the first switch reload. `show archive config differences nvram:startup-config system:running-config` showed exactly what was unsaved before I committed to `write memory`.
2. At an IOS `Destination filename [...]?` prompt, press Enter to accept the default. Typing `Y` makes `Y` the filename.
3. "Activation of logical volume pve/data is prohibited while logical volume pve/data_tmeta is active" means the thin pool's components were activated without the pool. Deactivate the stray components, then let the pool assemble. Check the boot journal for a `thin_check` failure first; with damaged metadata, this is a different and more careful repair.
4. A command that hangs on LVM is often waiting on the VG lock behind another LVM operation. Check with `ps` before killing anything, and never interrupt `thin_check`.
