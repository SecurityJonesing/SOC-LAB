# 3.3 Hookscript Persistence and Duplicate Filter Fix

**Phase:** 5, Network Visibility (SPAN and Suricata)
**Step:** 3, East West Gap and Mirroring
**Status:** Designed one session, applied and verified end-to-end the next (2026-09-08). Working and confirmed on live hardware. Phase 5's tc mirror persistence item is closed.

**Note on scope:** Phase 5 was paused under the active job-search priority freeze when this was applied. Explicitly and deliberately unpaused for this one persistence task; the phase returns to paused afterward unless separately reopened.

## Why this step exists

The tc mirror rules from Step 3 (3.2) live in kernel memory only. They do not survive a `pve01` reboot, and restarting either mirror source VM (Kali, VM 100, or the Win11 victim, VM 101) recreates that VM's tap interface and silently drops its mirror while the other keeps working. This is the one remaining item keeping Phase 5 from being called fully done.

## Design decided

Three VMs can each break mirroring if restarted:
- VM 100 (Kali), tap `tap100i0`, a mirror source
- VM 101 (Win11 victim), tap `tap101i0`, a mirror source
- VM 103 (wazuh-host), tap `tap103i1`, the mirror destination. Its tap gets recreated on restart; whether filters on 100/101 still resolve it by name afterward was not verified in the existing build log.

Decision: apply the same "re-check both mirrors" logic on any of the three VMs starting, not just the two sources, so a wazuh-host restart also triggers a re-check.

## Planned implementation

**1. One shared, idempotent script**, `/var/lib/vz/snippets/apply-suricata-mirrors.sh`. Loops over a `SRC_TAPS` array (`tap100i0 tap101i0`), checks each source tap and the destination tap (`tap103i1`) exist before acting, adds the `clsact` qdisc only if missing, adds the `mirred` mirror filter only if an identical one isn't already present, and logs every action (or skip) to `/var/log/suricata-mirror-hook.log`. **The idempotency check must match `tc`'s display format (`Egress Mirror to device <tap>`), not its command syntax** — see the bug section below; the first version of this script got that wrong.

**2. A hookscript wrapper**, `/var/lib/vz/snippets/suricata-mirror-hook.sh`. Proxmox hookscripts receive `<vmid> <phase>` as arguments; the wrapper runs the shared script only when `PHASE = post-start`, so one file can be attached to all three VMs.

**3. Attach to all three VMs:**
```
pvesm status --content snippets   # confirm snippets storage enabled first, not on by default
chmod +x apply-suricata-mirrors.sh suricata-mirror-hook.sh
qm set 100 --hookscript local:snippets/suricata-mirror-hook.sh
qm set 101 --hookscript local:snippets/suricata-mirror-hook.sh
qm set 103 --hookscript local:snippets/suricata-mirror-hook.sh
```

## Rollback path (stated per standing rule, before any change is applied)

Everything here is additive: two new files under `snippets/`, and a `--hookscript` pointer set on three VM configs. Nothing touches `vmbr1`, `vmbr3`, or pfSense. Full undo: `qm set 100/101/103 --delete hookscript`, then delete the two script files. Worst case if something is wrong: the hookscript fails or does nothing, leaving today's actual state unchanged (mirrors present until the next restart). It cannot break a currently working mirror, since it only adds filters, never removes them.

## Start-order question, resolved by design

A full `pve01` reboot starts all three VMs, firing each one's `post-start` hookscript, so this covers a full reboot without a separate systemd unit. If VM 103 comes up before 100/101, its own hookscript run correctly skips (source taps not present yet); when 100/101 start afterward, their runs find `tap103i1` present and add the filters correctly. Start order does not need to be controlled.

## Extension pattern for future RANGE30 VMs (Phase 7: `dc01`, `win11-ws02`, `linux-victim`)

When a new RANGE30 VM is built:
1. Add one entry to `SRC_TAPS` in the shared script, e.g. `SRC_TAPS=(tap100i0 tap101i0 tap104i0)`.
2. Attach the same shared hookscript: `qm set 104 --hookscript local:snippets/suricata-mirror-hook.sh`.

Nothing else changes: the shared script already loops over `SRC_TAPS`, and a fresh VM's own `post-start` applies its own mirror on first boot without needing to re-run anything on the existing VMs. Tap names are predictable from VM ID (`tap104i0` for VM 104's first NIC) but should be confirmed with `ip -br link show | grep tap104` after first boot rather than assumed.

## The bug: idempotency check never matched, silently stacked duplicates

Restarting VM 101 fired the hook correctly, but the log revealed a problem. `tap101i0` (the VM actually restarted) logged both `ADDED clsact qdisc` and `ADDED mirror filter`, which is correct: restarting a VM destroys and recreates its tap, wiping all `tc` state, so rebuilding from nothing is right. But `tap100i0` (Kali, never restarted) also logged `ADDED mirror filter`, with no accompanying qdisc line. That combination is the tell: the qdisc was already there, so the filter was too, and the script should have logged `OK ... already mirroring` instead of adding a second one.

`tc filter show dev tap100i0 ingress` confirmed two independent filters (`pref 49151` and `pref 49152`), each with its own `mirred` action doing the identical mirror to `tap103i1`.

**Root cause.** The original check was:
```
grep -q "mirred.*egress mirror.*dev $DST_TAP"
```
Real `tc filter show` output reads `mirred (Egress Mirror to device tap103i1)` — capitalized, `to device` rather than `dev`, wrapped in parentheses. The pattern never matched, so the check silently always failed and always re-added. Because the design deliberately re-checks *both* source taps whenever *any* of the three VMs starts, this would have compounded a fresh duplicate mirror filter on every VM start indefinitely.

Worth recording why this got through: the pattern was written from how the `tc` command is *typed*, not from how `tc` *displays* existing state. Those differ, and nothing in the plan review caught it because the plan was reviewed against the man page rather than against live output from this host.

**Fix**, verified against live output before writing it:
```
grep -q "Egress Mirror to device $DST_TAP"
```
Confirmed empirically first by piping the real filter output through the proposed pattern (`tc filter show dev tap101i0 ingress | grep -o "Egress Mirror to device tap103i1"`) and checking it actually matched, rather than assuming a second time. Then the script was rewritten with the corrected line, and the existing duplicate on `tap100i0` removed with `tc filter del dev tap100i0 ingress pref 49152`, leaving one filter.

## Live-fire verification

Three false starts before a real test, worth noting since each looked like a hookscript failure and was not:
1. `qm reboot 100` appeared to do nothing. `qm status 100 --verbose` showed uptime still climbing and an unchanged PID.
2. Cause: Kali's XFCE desktop intercepts the ACPI signal and displays a logout dialog, waiting for a human click. The `qm` command returns immediately, so it looks like a silent failure while the VM sits at the prompt.
3. Clicking Restart in that dialog also failed to take, PID still unchanged.

Resolved with a forced power cycle, which is the more meaningful test anyway since it matches the real scenario this work exists to survive (host reboot, crash, unexpected restart), and cannot be intercepted by the guest:
```
qm stop 100
qm status 100     # confirmed "status: stopped" before restarting
qm start 100
```
Confirming `stopped` as its own step mattered here, given three prior assumed-restarts that never happened.

**Result** (`/var/log/suricata-mirror-hook.log`):
```
2026-09-08T10:26:51-05:00 ADDED clsact qdisc on tap100i0
2026-09-08T10:26:51-05:00 ADDED mirror filter: tap100i0 -> tap103i1
2026-09-08T10:26:51-05:00 OK tap101i0 -> tap103i1 already mirroring
```
Both behaviors proven in one run: `tap100i0` correctly rebuilt from nothing after its tap was destroyed, and `tap101i0` correctly recognized as already mirroring and skipped. That `OK` line is the one the broken pattern could never produce.

Final state confirmed with `tc filter show` on both taps: exactly one `mirred (Egress Mirror to device tap103i1)` action each, no duplicates.

## Outcome

tc mirror persistence works. Mirrors survive individual VM restarts and, by the same mechanism, a full `pve01` reboot (which starts all VMs, firing each one's `post-start`). Phase 5 is complete.
