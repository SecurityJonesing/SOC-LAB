## Why this step exists

The tc mirror rules from Step 3 (3.2) live in kernel memory only. They do not survive a `pve01` reboot, and restarting either mirror source VM (Kali, VM 100, or the Win11 victim, VM 101) recreates that VM's tap interface and silently drops its mirror while the other keeps working. This is the one remaining item keeping Phase 5 from being called fully done.

## Design decided

Three VMs can each break mirroring if restarted:
- VM 100 (Kali), tap `tap100i0`, a mirror source
- VM 101 (Win11 victim), tap `tap101i0`, a mirror source
- VM 103 (wazuh-host), tap `tap103i1`, the mirror destination. Its tap gets recreated on restart; whether filters on 100/101 still resolve it by name afterward was not verified in the existing build log.

Decision: apply the same "re-check both mirrors" logic on any of the three VMs starting, not just the two sources, so a wazuh-host restart also triggers a re-check.

## Planned implementation

**1. One shared, idempotent script**, `/var/lib/vz/snippets/apply-suricata-mirrors.sh`. Loops over a `SRC_TAPS` array (`tap100i0 tap101i0`), checks each source tap and the destination tap (`tap103i1`) exist before acting, adds the `clsact` qdisc only if missing, adds the `mirred` mirror filter only if an identical one isn't already present, and logs every action (or skip) to `/var/log/suricata-mirror-hook.log`. Safe to run any number of times.

**2. A hookscript wrapper**, `/var/lib/vz/snippets/suricata-mirror-hook.sh`. Proxmox hookscripts receive `<vmid> <phase>` as arguments; the wrapper runs the shared script only when `PHASE = post-start`, so one file can be attached to all three VMs.

**3. Attach to all three VMs:**
```
pvesm status --content snippets   # confirm snippets storage enabled first, not on by default
chmod +x apply-suricata-mirrors.sh suricata-mirror-hook.sh
qm set 100 --hookscript local:snippets/suricata-mirror-hook.sh
qm set 101 --hookscript local:snippets/suricata-mirror-hook.sh
qm set 103 --hookscript local:snippets/suricata-mirror-hook.sh
```

## Rollback path (stated per standing rule, before any change is applied)

Everything here is additive: two new files under `snippets/`, and a `--hookscript` pointer set on three VM configs. Nothing touches `vmbr1`, `vmbr3`, or pfSense. Full undo: `qm set 100/101/103 --delete hookscript`, then delete the two script files. Worst case if something is wrong: the hookscript fails or does nothing, leaving today's actual state unchanged (mirrors present until the next restart). It cannot break a currently working mirror, since it only adds filters, never removes them.

## Start-order question, resolved by design

A full `pve01` reboot starts all three VMs, firing each one's `post-start` hookscript, so this covers a full reboot without a separate systemd unit. If VM 103 comes up before 100/101, its own hookscript run correctly skips (source taps not present yet); when 100/101 start afterward, their runs find `tap103i1` present and add the filters correctly. Start order does not need to be controlled.

## Extension pattern for future RANGE30 VMs (Phase 7: `dc01`, `win11-ws02`, `linux-victim`)

When a new RANGE30 VM is built:
1. Add one entry to `SRC_TAPS` in the shared script, e.g. `SRC_TAPS=(tap100i0 tap101i0 tap104i0)`.
2. Attach the same shared hookscript: `qm set 104 --hookscript local:snippets/suricata-mirror-hook.sh`.

Nothing else changes: the shared script already loops over `SRC_TAPS`, and a fresh VM's own `post-start` applies its own mirror on first boot without needing to re-run anything on the existing VMs. Tap names are predictable from VM ID (`tap104i0` for VM 104's first NIC) but should be confirmed with `ip -br link show | grep tap104` after first boot rather than assumed.
