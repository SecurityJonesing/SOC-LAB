# Step 3: First Agent Enrolled

## 2026-08-04, Victim VM moved to Range VLAN, isolation proven live, Sysmon + Wazuh agent deployed

**Phase:** 3 (Step 6, closeout, Phase 3 done)
**Goal:** Move the Windows victim VM onto RANGE30, prove the Phase 2 isolation rule against a real VM for the first time, then instrument it with Sysmon and the Wazuh agent so it reports to the manager.
**Rollback:** No Proxmox snapshot for the VLAN move (VM was off). pfSense config exported before the new 1515 rule.
**Transcript:** Proxmox web UI via Claude in Chrome, PowerShell 7 and Windows PowerShell on the management PC, PowerShell on the victim VM's own console.

### What happened

VLAN move. Confirmed the victim VM was powered off. Via Proxmox's Hardware tab, changed the network device from the flat bridge to the LAN-trunk bridge tagged VLAN 30. MAC address and NIC model left untouched.

Isolation proven live, the real Phase 2 acceptance check, finally run. Booted the VM. Confirmed a clean DHCP lease on the Range subnet, gateway matching RANGE30's. From inside the VM:
- Ping to a public IP: 100% loss (no internet), expected.
- Ping to the home router: 100% loss (no home network), expected.
- A TCP test to the Wazuh host on port 1514: succeeded, expected (the ingest port is specifically allowed, plain ICMP would have failed since the rule is TCP/1514-only).

This closes the caveat that had been sitting in the log since the isolation rule was written, the rule was correctly configured but never actually tested against a live VM until now.

Staging tools onto an intentionally internet-less VM. Since RANGE30 has zero outbound internet by design, Sysmon, the SwiftOnSecurity config, and the Wazuh agent MSI all had to be downloaded on the management PC and transferred in via virtual media rather than a direct download inside the VM.

Confirmed current versions live: Sysmon (current release), Wazuh agent pinned to 4.14.6 specifically, matching the manager's version exactly, since agent version must be less than or equal to manager version.

Built an ISO from the staging folder to attach as virtual media, took several failed attempts:
1. First script used a direct `.Read()` call on the COM stream object, failed with "does not contain a method named 'Read'" in PowerShell 7.
2. Switched to Windows PowerShell 5.1, same error, ruling out a PowerShell-version-specific theory.
3. Root cause (confirmed via web search): this is a long-standing, version-independent limitation, the underlying COM interface is low-level with no dispatch layer, so PowerShell fundamentally cannot call `.Read()` on it directly, in any version. The fix is a small inline C# helper class, compiled at runtime, that does the raw marshaling correctly.
4. Used that pattern, worked immediately. ISO built and verified.

Uploaded the ISO to Proxmox's `local` storage, this step had to be done directly since selecting a local file for upload requires the OS's native file picker. Attached the ISO to the victim VM's CD/DVD drive. Confirmed inside the VM: all three files visible.

Sysmon installed. Copied files to a local tools folder, extracted, installed with the SwiftOnSecurity config in an elevated PowerShell window, clean install, schema validated, driver and service both installed and started with no errors. Verified real events flowing, DNS queries, process creation with full hash/parent-chain detail.

Wazuh agent installed, hit a real gap, fixed it. Installed via a silent MSI install pointed at the manager's IP, the install returned cleanly but the service was stopped, not auto-started. Started it manually, the log showed a repeating cycle: requesting an enrollment key, unable to connect to the enrollment service on port 1515. `client.keys` was empty, confirming enrollment never completed.

Root cause: the same "OPT/segment interfaces get zero rules by default" pattern that hit INFRA20 three times during Phase 3, this time on RANGE30. The existing isolation rule only covered port 1514 (ongoing agent-to-manager data traffic), a Windows agent's first-time enrollment handshake needs a separate one-time connection to port 1515.

Wrote and applied a new pfSense rule on RANGE30: Pass, RANGE30 subnets to INFRA20 subnets, TCP, port 1515, description "allow RANGE30 -> Wazuh enrollment (1515)". Applied cleanly.

Retried enrollment, restarted the service, checked `client.keys`, now populated with a real agent ID, name, and registration key. Log confirmed a successful connection to the manager and "Agent is now online."

Confirmed in the Wazuh dashboard directly: agent ID `001`, correct name, correct IP, OS correctly identified, status active, agent version matching the manager exactly, group `default`.

### Outcome

- Phase 3 Step 6 is complete. The victim VM is on RANGE30, isolation is proven live, Sysmon is capturing detailed telemetry with the SwiftOnSecurity ruleset, and the Wazuh agent is enrolled, connected, and reporting.
- Phase 3 is now fully complete, Docker/Git substrate, Wazuh deployed and password-secured, first real endpoint instrumented and confirmed reporting end to end.
- RANGE30 now has 3 firewall rules: Pass (1515, Wazuh enrollment), Pass (1514, Wazuh ingest), Block (default deny, everything else).
- Reusable technique captured: the ISO-staging pattern (download on the management PC, build ISO via the COM/C# workaround, upload to Proxmox, attach as virtual CD) is now a proven path for getting tools onto any isolated Range VM.
- The attack VM (Kali) is still on the flat network, not yet moved to Range VLAN.
- Phase 4 (Detection Engineering) is next.

### Lessons

1. A firewall rule can be correctly configured and still not be "proven," don't mark an acceptance check complete until it's actually been run against real traffic.
2. Every new VLAN/segment's "zero rules by default" gap can bite more than once, in different directions. Check both ongoing traffic ports and one-time enrollment/handshake ports when standing up any new agent-based service.
3. A low-level COM stream's `.Read()` method cannot be called directly from PowerShell, in any version, the fix is always a small compiled C# helper.
4. Silent installer success doesn't mean the installed service actually started or connected.
5. When picking a package version for a new tool, check compatibility constraints explicitly (agent less than or equal to manager, in this case).
6. A browser-automation tool's controlled tabs closing unexpectedly is a real, if intermittent, failure mode, falling back to "build it directly, verify via screenshot afterward" is a reasonable recovery pattern.
7. A password typed during a session lives in that session's raw transcript regardless of care taken afterward, the fix is discipline about never repeating it back in chat or writing it into any tracked documentation, not pretending it can be scrubbed retroactively.
