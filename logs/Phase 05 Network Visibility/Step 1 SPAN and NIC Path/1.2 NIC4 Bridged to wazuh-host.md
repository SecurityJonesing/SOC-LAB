## 1.2 NIC4 Bridged to wazuh-host

**Phase:** 5, Network Visibility (SPAN and Suricata)
**Goal:** Bring up the SPAN destination NIC (`eno4`/NIC4) on `pve01`, then get that mirrored traffic onto `wazuh-host` (the Infra host, per `LAB-BLUEPRINT.md`) so Suricata can eventually bind to it there, continuing directly from the switch side SPAN session work.
**Rollback:** `pve01` side, additive only (`ip link set` state change on an otherwise unused interface, new `vmbr4` bridge containing only `eno4`), reversible with `ip link set eno4 down` or removing the `vmbr4` stanza from `/etc/network/interfaces`. `wazuh-host` side, additive only (new `net1` device), reversible by removing it from the VM's Hardware tab in Proxmox. Neither side touched `vmbr1`/`net0` or existing Wazuh container config. No VM snapshot taken, judged unnecessary for this class of change.
**Transcript:** PowerShell `Start-Transcript` covering the `pve01` SSH session (KEX workaround used, standard). `wazuh-host` session was not logged locally this time.

### What happened

**Architecture check before starting.** `LAB-BLUEPRINT.md`'s spec for this phase calls for the SPAN destination to be passed through to the Wazuh and Infra host, not left on `pve01`'s own host OS, this was not obvious from the earlier NIC4 bring up alone, and changes what "install Suricata" means (on `wazuh-host`, not `pve01`). Caught and confirmed before proceeding.

**pve01 side, NIC4 bring up, confirmed:**
```
ip link show eno4
```
Confirmed `state DOWN`, `qdisc noop`, matches a known gotcha (NICs not administratively up by default). Brought it up:
```
ip link set eno4 up
ip link set eno4 promisc on
```
Verified: `state UP`, `LOWER_UP` (carrier confirmed, matching the switch side connected status), `PROMISC` present in flags.

**Passthrough method, decided: bridge plus virtual NIC, not full PCI passthrough.** Two options were considered: true PCI passthrough of `eno4` to `wazuh-host` via `vfio-pci`, same mechanism as the GPU passthrough on the AI node, requires IOMMU/VT-d and carries real risk of a botched IOMMU group; or a dedicated Linux bridge on `pve01` containing only `eno4`, with `wazuh-host` given a second virtual NIC attached to it. Chose the bridge option, lower friction, no BIOS/IOMMU work, easily reversible, functionally equivalent for Suricata's needs.

**Created `vmbr4` on `pve01`.** Checked current bridge config first, three existing bridges (`vmbr1` management/static, `vmbr2` pfSense WAN, `vmbr3` pfSense LAN trunk), `eno4` already auto listed as `iface eno4 inet manual` but unattached. Added, via `nano /etc/network/interfaces`:
```
auto vmbr4
iface vmbr4 inet manual
        bridge-ports eno4
        bridge-stp off
        bridge-fd 0
```
Matches the existing bridge stanza style exactly, no IP, no VLAN awareness needed. Applied live:
```
ifreload -a
```
Verified: `vmbr4` up and live (inherited `eno4`'s MAC, standard for a single member bridge); `eno4` now shows `master vmbr4`; `vmbr1`/`vmbr2`/`vmbr3` unchanged, same interface numbers, no drift.

**Added a second NIC to `wazuh-host` via the Proxmox web UI.** VM 103, Hardware, Add, Network Device, Bridge `vmbr4`, no VLAN tag, firewall unchecked. Came up as `net1`. Hotplugged cleanly, no VM reboot needed, so the running Wazuh containers were never disrupted.

**wazuh-host side, new NIC bring up.** `ip link show` confirmed the new interface as `ens19` (Ubuntu predictable naming), `state DOWN`, `qdisc noop`, no IP, same clean starting state as `eno4` had on `pve01`. Brought it up the same way:
```
sudo ip link set ens19 up
sudo ip link set ens19 promisc on
```
Verified: `UP`, `LOWER_UP`, `PROMISC` all present.

**Persistence decision, deferred, not configured yet.** Current `ip link set` state on both `eno4` and `ens19` is runtime only, a reboot of either host resets it. Decided to let Suricata's own install and service own bringing the interface up and setting promiscuous mode going forward, rather than hand writing a second, separate persistence mechanism.

### Outcome
Full mirrored traffic path is live end to end, confirmed at every hop: switch (`Gi1/0/4`, mirroring VLAN 30) to `pve01` `eno4` to `vmbr4` bridge to `wazuh-host` `ens19`. All interfaces up, all promiscuous where needed, no IPs assigned anywhere in the path (correct, this is a monitoring only path, not a routed one). `wazuh-host`'s existing INFRA20 NIC (`ens18`/`net0`) and Wazuh container stack were untouched throughout.

This closes the SPAN and NIC path step of this phase. Two steps remain: install Suricata on `wazuh-host` and bind it to `ens19`, integrating `eve.json` into Wazuh; then acceptance check, `nmap -sS` from Kali shows up in Wazuh from Suricata and triggers a host based alert, same event, two detection layers.

### Lessons
1. `LAB-BLUEPRINT.md`'s exact wording mattered here, "pass it through to the Wazuh and Infra host" was easy to read past when the immediate, visible next step already felt like progress. Worth explicitly re checking the blueprint's exact phase steps before starting an install.
2. Bridge plus virtual NIC is a solid, low risk substitute for true PCI passthrough when the goal is just giving a VM a dedicated interface, not requiring exclusive physical device ownership.
3. A VM's newly added virtual NIC hotplugs cleanly on this Proxmox and Ubuntu combination, no reboot was needed.
4. `Start-Transcript` must be typed as one complete, unbroken line with quotes intact, a truncated paste either leaves PowerShell hanging on a continuation prompt, or throws a parameter error once the unquoted path's spaces get parsed as separate arguments.
